# ADR 0013: The Attempt Gate Owns Sittings, Tokens, Devices, And Answers

## Status

Accepted on 13 October 2026 with owner decisions K14 and K18. The owner approved
decisions K1 to K20 on that day. One part is live: the live-attempt gate in
`confect/assessment/gate` admits every try-out answer and section finish
(#1040). Everything else in this ADR is planned: the sittings, tokens, proctor
actions, devices, the closing and reconciling states, late records, sections, and
the offline queue.

The School program has three delivery waves, A, B, and C, in that order. Wave A
is the foundation, wave B is the core School, and wave C adds the rest. Their
dates are plan estimates and are not part of this decision. The gate is decided
in program wave A and the rest of it ships with the engine cutover in program
wave B, as ADR 0031 describes.

## Context

A try-out and a school exam use one attempt model. Today the try-out start lives
in `packages/backend/confect/tryouts/start`. The answer and section finish
mutations live in `packages/backend/confect/tryouts/mutations` and pass the
live-attempt gate through the try-out store in
`packages/backend/confect/tryouts/gate.ts`. School exams do not exist on main
yet.

A proctored sitting needs more than a try-out does:

- a schedule that the server enforces, because queries never read the clock
  (ADR 0011, Time);
- a short token that a student types to enter a sitting, and that a proctor can
  change;
- one device per attempt, and a proctor's approval to move it to another device;
- answers that survive a dropped connection and reach the server in order;
- proctor actions that the journal can explain afterwards; and
- integrity signals, which never include a camera, a face, a voice, or emotion
  (K14).

## Decision

### Attempt lifecycle

An attempt is in one of these states: `ready`, `inProgress`, `locked`,
`closing`, `reconciling`, `submitted`, `grading`, `graded`, or `released`. The
exam profile owns the write allowance and the reconciliation grace period that
the states use (ADR 0032).

- `ready`: the student can start the attempt.
- `inProgress`: the student is answering.
- `locked`: a proctor has locked the sitting, so the student cannot answer. The
  time keeps running and the queue keeps syncing. Unlocking returns the attempt
  to `inProgress` before the deadline and to `closing` after it. A locked attempt
  that is past its deadline takes records as `closing` does.
- `closing`: the deadline passed on the server clock and the server has not
  closed the attempt yet. This window lasts one presence lease (see the offline
  queue). The screen takes no answers. A record that reaches the server in it
  follows the rules of Late records, and a Finish is accepted so that the
  manifest can complete.
- `reconciling`: the device's queue manifest had not arrived complete when the
  attempt closed (see the offline queue). The attempt takes no new answers from
  the screen. A record that reaches the server in it follows the rules of Late
  records. The attempt moves to `submitted` when the profile's grace period ends,
  or earlier once every version the manifest names has arrived. Scoring never
  starts from this state.
- `submitted`: the attempt is closed to the screen and waits to be scored. It
  gets here when its Finish is accepted with the manifest complete, when the
  server closes it with the manifest complete, or when reconciliation ends. If the
  grace period ended with the manifest incomplete or absent, the attempt is
  `submitted` marked incomplete, and what never arrived is a missing record: each
  version the manifest names, or the manifest itself. A record that reaches the
  server in this state follows the rules of Late records. Scoring starts when no
  late record and no missing record of the attempt waits for a decision.
- `grading`, `graded`, `released`: scoring has started, and the attempt waits for
  a grade, has a grade, and shows the grade to the student under the school's
  release policy (ADR 0031, grading).

### Sittings

A sitting is one run of an exam for one group in one room, with one token. The
server schedules the opening and the closing of each sitting. Opening and
closing are scheduled mutations, because queries never read the clock (ADR
0011). A proctor who closes a sitting early runs the same closing at that
moment, so every way a sitting ends goes through the offline check below.

### Proctor actions

Each proctor action has a rule and a record. Every action writes a journal entry
(ADR 0016) and stores its reason when it needs one. Every action, the decision
on a late record included, is open to the Session proctor of that sitting, to
the author of its exam, to an Admin of its school, and to every Owner, as the
blueprint's row "Awasi sesi" sets it (ADR 0012). A Principal and a Deputy see
the participant dashboard of a sitting and take no action. The decision on a
late record is an action on the attempt, so it works after the sitting has
closed.

| Action | Rule | Recorded |
| --- | --- | --- |
| Lock the sitting | Only after a signal and the proctor's confirmation. Students cannot answer until the sitting is unlocked, and the time keeps running. Lock stops the screen and not the queue: records keep syncing while the attempt is locked. A technical fault uses Add minutes instead. | Yes, with a reason |
| Unlock the sitting | A reason is required. Before the deadline the attempt returns to `inProgress`. After the deadline it goes to `closing`. | Yes, with a reason |
| Add minutes | For a valid event, such as a power cut. The proctor enters the number of minutes. It is allowed only before the deadline. It moves the deadline and the scheduled close, and it never changes a record already marked late. | Yes, with a reason and the minutes |
| Change the token | The old token stops working. Students who are already inside keep working. | Yes |
| Allow a second device | Moving an attempt to a session on another device needs the proctor's approval. The earlier session is retired at that moment and writes nothing after it. | Yes |
| Close the sitting | The deadline of every open attempt becomes now, and each closes as at a scheduled deadline: submitted with the answers the server holds when its manifest is complete one presence lease later, and `reconciling` otherwise (see the offline queue). | Yes |
| Accept a late record | Only for a record of this sitting synced after the deadline, before its attempt is scored. The record becomes the item's answer when its version is the newest one accepted for that item. | Yes, with the record and its version |
| Reject a late record | The same scope, and a reason is required. The record stays in the event log and does not count. A missing record is rejected the same way, and it does not count if it arrives later. | Yes, with the record, its version, and a reason |

What an action does depends on the state of the attempt it reaches. Change the
token and Allow a second device act on the sitting and its devices, so the state
of an attempt does not change them.

| Action | `inProgress` | `locked` | `closing` | `reconciling` |
| --- | --- | --- | --- | --- |
| Lock | The attempt becomes `locked`. The queue keeps syncing. | No change. | Refused. | Refused. |
| Unlock | Refused. | Before the deadline, `inProgress`. After it, `closing`. | Refused. | Refused. |
| Add minutes | Moves the deadline and the scheduled close. | The same, before the deadline only. | Refused. | Refused. |
| Close the sitting | The deadline becomes now, so the attempt becomes `closing`. | The deadline becomes now, and the attempt stays `locked` until the close. | No change. | No change. |
| Accept or reject a late record | Allowed for a late record of an earlier section. | The same. | Allowed. | Allowed. |

The close applies to a locked attempt as to any other. A locked attempt is closed
one presence lease after its deadline, and the lock does not delay it.

### Tokens

- A token has six characters, such as `K7Q4XM`. The alphabet has no I, O, 0, or
  1.
- The server stores a keyed hash of the token. It never stores the token itself.
- The token changes when a proctor changes it, or at the interval that the school
  sets.
- A device may try five times a minute.
- A token admits a student to a sitting, and admission hands out the key of the
  sitting's bundle. A school exam's bundle is encrypted with one key per sitting
  (ADR 0031, section 8), so a cached bundle file is useless without admission.
  The gate gives the key to a device session when the token admits it, and to a
  new session of an attempt that was already admitted. It never sends the key
  with the bundle, and changing the token does not take it from a student who is
  already inside. The device keeps the key until the attempt ends. A consumer
  try-out has no token, and its bundle holds only what a learner may see before
  answering, so it has no bundle key.

### Devices and the offline queue

- An attempt is bound to one device session at a time. Allow a second device
  (see Proctor actions) moves the attempt to a session on another device: from
  the approval on, the earlier session is retired and writes nothing, and a record
  it sends later is refused and stays in the attempt's event log as the record of
  a retired session. So two sessions never number the versions of one item at
  once, and Finish, with its manifest, comes only from the bound session. What
  the earlier device had not sent before the approval is lost with it, as for a
  device that was reset, and the event log records the move.
- The device numbers the versions of each item. When a device binds to the
  attempt, it starts from the version the server holds for each item, so a
  session the attempt moved to, or a session that was reset, continues from the
  server.
- The offline queue lives in IndexedDB on the device. It holds one record per
  answer, with the attempt, the item, and the version of the answer. It is
  encrypted with a key that the server issues to the bound device session at the
  start of the attempt. The key belongs to the attempt, so a consumer try-out has
  one too, and a new device session gets a new key. A device that was reset
  cannot read its old queue. The records in it that the server already holds are
  safe, and the ones it had not sent are lost with it. This is the one loss that
  the queue cannot prevent, and it is never silent: when the new session binds to
  the attempt, the attempt's event log records the replacement with the time the
  old session was last online. In a sitting, the proctor sees the replacement and
  can add minutes for a student who must answer again (see Proctor actions).
- On reconnection the queue sends its records in order, per item version. The
  server refuses a version that is not newer than the one it holds, a resent
  record included. The device drops a refused record from its queue, and the
  queue behind it goes on.
- The deadline is the server's. The device clock never decides a deadline. A
  write compares the server clock with the deadline itself, so a scheduled
  transition that runs late never lets a late record count as on time.
- When a write does not reach the server, the screen returns to the server's
  value and the record stays in the queue until it is sent. A record that the
  server refuses leaves the queue and stays in the attempt's event log with its
  reason, so no answer disappears without a trace.
- A record that reaches the server within the exam profile's write allowance
  after the deadline counts as on time. The allowance is a few seconds and never
  longer than one presence lease, so it covers a write in flight at the deadline
  and bounds the time it can add.
- Finish is the last record of the queue. Pressing it freezes the queue, and
  the device sends it after every answer record, with the manifest: the newest
  version it holds for each item. The server accepts Finish only when every
  version the manifest names has arrived, and otherwise answers which ones are
  missing, so the device sends them and Finish again. A version that a newer one
  already on the server has superseded counts as arrived. A device that goes
  offline after Finish keeps its frozen queue, and the deadline closes the
  attempt by that manifest as below. So no answer the device holds is lost
  without a trace: it is counted, kept for a decision, or refused with its reason
  in the event log. A Finish that arrives while the attempt is `closing` is
  accepted so that the manifest can complete, and its versions that arrive after
  the write allowance keep the late mark. A Finish sent again to a `submitted`
  attempt answers success and changes nothing, because submit is idempotent (ADR
  0031).
- When the deadline passes, every device freezes its queue and sends its
  manifest: the newest version it holds for each item. A device that is offline
  sends it when it reconnects. From the deadline the attempt is `closing`. One
  presence lease after the deadline the server closes the attempt: it is
  submitted with the answers the server holds when the manifest has arrived and
  every version it names has arrived, and it moves to `reconciling` for the
  profile's grace period otherwise. Presence only times the close: the lease is
  how long presence keeps a silent session online, 2.5 heartbeat intervals in
  `@convex-dev/presence` 0.4.0 (`heartbeat` in its `component/public.ts`), plus
  the second its disconnect worker may wait, so a connected device's manifest has
  arrived by then. Whether the device is online never decides the close, because
  a live connection does not prove that its last write arrived.
- The close is a scheduled mutation. The cron sweep that ADR 0011 requires for
  time-driven states also closes any attempt left in `closing` past one presence
  lease and ends any `reconciling` past its grace period, so a lost schedule
  never leaves an attempt open.
- Reconciliation ends early once every version the manifest names has arrived. A
  device that sends no manifest, or drops again halfway, leaves the attempt in
  reconciliation until the grace period ends. Then the attempt is `submitted`
  marked incomplete, and every record that reaches the server from then on
  follows the rules of Late records until scoring starts.

### Late records

A record that reaches the server after the write allowance is a late record. The
table gives the rule for each moment a record can arrive.

| When the record reaches the server | What happens |
| --- | --- |
| Before the deadline, or inside the write allowance after it | It counts. |
| After the allowance, until scoring starts: while the attempt is `closing`, `reconciling`, or `submitted` | It is kept as a late record. Arriving late is never a reason to refuse it. |
| Once scoring has started: in `grading`, `graded`, or `released` | It is refused with its reason. |

In every row a version that is not newer than the one the server holds is
refused, a resent record included, because a newer record already took its
place. The manifest bounds nothing in the table: it says which versions must
arrive, and a record is kept whether or not the manifest has arrived. Every
record stays in the attempt's event log, a refused one with its reason.

Version order cannot prove that a record was written before the deadline, so a
kept late record never counts by itself. A version that the manifest names and
that has not arrived when the grace period ends is a missing record, and so is
the manifest when it has not arrived. In a proctored sitting, whoever may decide
a late record (see Proctor actions) accepts or rejects each late record and
rejects each missing record that will not arrive, and the attempt is scored once
reconciliation has ended and every late record and every missing record has a
decision. A record that nobody decides stays undecided: the grade of the attempt
waits, the review queue lists the attempt (`/exams/{exam}/review`, ADR 0026), and
no default decides it. In an attempt without a proctor, such as a consumer
try-out, a late record and a missing record do not count, and the attempt is
scored once reconciliation has ended.

### Sections and breaks

An exam has sections (ADR 0031), and the exam profile sets the time of each
section and the total time.

- A section has its own deadline, and its clock starts when the section opens.
- Ending a section, by the student or at its deadline, is a section end and not a
  Finish. The attempt stays `inProgress`, in the next section or in the break
  before it, and the attempt's Finish follows the last section. A section end by
  the student works like a Finish for that section: the device freezes the
  section's queue and sends it with the section's manifest, and the server
  accepts the end when every version the manifest names has arrived.
- The rules of the deadline apply to the deadline of each section: the write
  allowance, the late records, and the decision on them. The states `closing`,
  `reconciling`, and `submitted` belong to the end of the attempt, which is the
  deadline of the last section or the total time. A record of an earlier section
  that arrives after its write allowance is a late record, and the attempt
  carries on.
- A break is a gap between two sections in which the gate takes no answers. The
  next section's clock starts when it opens.
- Add minutes moves the deadline of the section in progress and the total
  deadline with it. Close the sitting ends the section in progress and the
  attempt with it.
- The gate keeps the behavior of the live try-out
  (`packages/backend/confect/tryouts/mutations/expiry.ts`): when a section's time
  runs out, the section ends and the attempt continues, unless the total time of
  the attempt has run out too, which ends the attempt.

### Presence

One mechanism serves two uses: a proctored sitting, and the collaborative
editor, planned as `confect/editor`. Both use the `@convex-dev/presence`
component. The repository has no such component yet. Wave B installs it at
version 0.4.0. The proctor's dashboard reads from it whether a device is online,
the gate takes from it only the lease that times the close, and no presence
table or heartbeat is written by hand.

### Targets

Each target stays a target until its test runs. None of them is measured yet.

| Measure | Target |
| --- | --- |
| Write an answer, p95 | Under 150 ms, on every surface |
| Start or submit an attempt, p95 | Under 300 ms |
| Sync queued answers after reconnection | Within 5 seconds |
| Answers lost while the connection is lost | Zero. The offline queue test drops the connection at random moments and checks every answer. A reset device is the one case it does not cover (see the offline queue) |
| Presence interval for a proctored sitting | Low. The exact interval is set by a load test |

A load test runs 1,000 participants in one sitting. That size is a target, and
the test parameters are assumptions until the test runs.

### Integrity signals

The web cannot lock a phone. Integrity therefore means signals, tokens, the
sitting lock, and Safe Exam Browser for an exam that asks for it. No signal
causes a sanction on its own. Signals are stored in clear, kept until the final
grade, and deleted with the exam. The table names the role that sees each one.

| Signal | How it is detected | Who sees it | What happens |
| --- | --- | --- | --- |
| Leaving the tab or app | `visibilitychange` | Proctor | A warning and a flag. The sitting locks only after the proctor confirms. |
| Losing window focus | `blur` | Proctor | A light flag |
| Leaving full screen | `fullscreenchange`, on desktop | Proctor | A flag. The student is asked to return. |
| Copy, paste, and context menu | `copy`, `paste`, `contextmenu` | Proctor | Recorded. A paste into an essay is marked. |
| A second device or tab | A device-bound session and `BroadcastChannel` | Proctor | A flag. A session on another device takes the attempt over only with the proctor's approval (see Allow a second device) |
| A long offline spell | Connection status and presence | Proctor | The duration is recorded. Answers stay on the device. |
| Time spent per item | The time spent on each item | Teacher only | An indication, not a verdict |
| Identical answers across attempts | Choice answers and short answers, by a simple rule that does not compare the meaning of a student's text | Teacher only | An indication, not a verdict |
| Camera, face, voice, or emotion | Not used | No one | Not collected in any country (K14) |

### Safe Exam Browser evidence

Safe Exam Browser (SEB) runs on Windows, macOS, and iOS. An exam that asks for it
accepts evidence from two channels:

| Platform | Evidence channel | Note |
| --- | --- | --- |
| Windows | The `X-SafeExamBrowser-ConfigKeyHash` header | The hash covers the absolute URL and the Config Key, so a proxy must rebuild the URL exactly |
| macOS | The SEB JavaScript API | The WKWebView build sends no header |
| iOS and iPadOS | The SEB JavaScript API | The same as macOS. An iPad test runs before an exam uses this rule |
| Android and Chromebook | None | The in-place path is used |

The header is sent only by the classic WebView, so every build is tested. An
attempt that shows evidence on neither channel is refused, but only on an exam
that requires SEB. Windows kiosk mode can stop third-party software from running
correctly under the SEB manual, so every exam that asks for SEB has an
alternative path.

### The gate module

The gate lives in `confect/assessment/gate` (ADR 0031). It exposes start, answer,
finish, and lock. It hides the sitting window and lock, the deadlines, the
device, the answer versions, and the accommodations frozen at start. One store
serves try-outs and school sittings. The answer mutation must meet the target
above, and the load test decides whether it does. Finishing runs through the
workpool.

### Accommodations at the gate

- Level 1, tools for everyone: a student sets them at any time. They never change
  the score.
- Level 2, supported settings: text to speech for maths and reading, contrast,
  and a separate room. A teacher or an admin sets them before the exam, and they
  apply from before the attempt starts.
- Level 3, recorded accommodations: extra time as a percentage, breaks, a reader
  or a scribe, or an alternative format. A school admin sets them with evidence.
  They are frozen when the attempt starts, and each change is recorded as an
  event.

Add minutes is a proctor action, not an accommodation. Before release, the
assessment player must meet WCAG 2.2 AA and be tested with NVDA, JAWS, and
VoiceOver.

## Consequences

- A sitting can also run on paper or on school computers in a supervised room.
  That path always exists (K14).
- A signal is a flag for a person to read. It is not a verdict, and the record
  shows who decided what.
- Who may see a signal is open between K14 and the planned privacy text, which
  names only teachers. The owner decides this before the privacy text describes
  signals.
- Every proctor action sits in the journal with its reason, so an appeal can see
  who locked a sitting and why.
- The latency figures are targets until each load test runs. Nothing in this ADR
  claims that they are met.

## Rejected Alternatives

- Camera, face, voice, or emotion checks, in any country (K14).
- A device lock. The web cannot lock a phone, so the design relies on signals,
  tokens, and the sitting lock instead.
- Deadlines on the device clock. A device clock can be changed, so the server
  clock decides every deadline.
